# Pattern Factory: Stratified Randomization of Organizations to Study Arms\n\n## Overview\n\nThis document describes the stratified randomization system for assigning ~1,500 FDA-cleared medical device manufacturers to three balanced study arms:\n- **Control Group**\n- **Treatment Arm 1**\n- **Treatment Arm 2**\n\nRandomization is **stratified by market tier** to ensure balanced distribution of Enterprise, Mid-Market, and Startup organizations across all arms.\n\n---\n\n## Algorithm\n\n### Stratified Block Randomization\n\nThe randomization process follows a **stratified block randomization** approach:\n\n1. **For each tier (1, 2, 3)**:\n   - Count all non-deleted organizations in that tier\n   - Compute balanced allocation:\n     - `control_count = tier_count ÷ 3`\n     - `treatment_1_count = tier_count ÷ 3`\n     - `treatment_2_count = tier_count ÷ 3`\n     - Distribute remainder orgs round-robin: control gets +1 if remainder ≥ 1, treatment_1 gets +1 if remainder ≥ 2\n\n2. **Randomize within tier**:\n   - Generate or use provided random seed\n   - Deterministically shuffle org list using seed + tier offset\n   - Assign first `control_count` orgs → 'control'\n   - Assign next `treatment_1_count` orgs → 'treatment_1'\n   - Assign remainder → 'treatment_2'\n\n3. **Result**: \n   - All organizations assigned to exactly one arm\n   - Each tier has balanced arms (within ±1 org)\n   - Each arm has roughly 500 orgs (assuming 1,500 total)\n\n### Tier Definitions\n\n- **Tier 1 (Enterprise)**: size > $500M — Strategic players, large manufacturers\n- **Tier 2 (Mid-Market)**: size $50M–$500M — Mid-market challengers\n- **Tier 3 (Startup)**: size < $50M — Pure-play AI startups\n\nSize is computed as: `MAX(5 × estimated_annual_sales, 10 × funding)`\n\n---\n\n## Database Schema\n\n### New Columns in `public.orgs`\n\n```sql\nALTER TABLE public.orgs ADD COLUMN study_arm TEXT \n  CHECK (study_arm IN ('control', 'treatment_1', 'treatment_2')) \n  DEFAULT NULL;\n\nALTER TABLE public.orgs ADD COLUMN randomization_seed BIGINT DEFAULT NULL;\nALTER TABLE public.orgs ADD COLUMN randomized_at TIMESTAMP DEFAULT NULL;\n```\n\n### is **deterministic**: using the same seed always produces the same assignments.\n\n### Re-running Randomization with Same Seed\n\n```bash\n# Original run\npython backend/scripts/randomize_orgs.py --seed 1234567890\n\n# Later, reproduce exact same allocation\npython backend/scripts/randomize_orgs.py --seed 1234567890\n\n# Verify same assignments\nSELECT id, study_arm FROM public.orgs WHERE deleted_at IS NULL ORDER BY id;\n```\n\n### Tracking Randomization History\n\nThe `randomization_seed` and `randomized_at` columns allow auditing:\n\n```sql\n-- View randomization history\nSELECT\n    event,\n    context ->> 'seed' AS seed,\n    context ->> 'timestamp' AS timestamp,\n    context -> 'arms' AS arm_counts,\n    created_at\nFROM public.system_log\nWHERE event = 'stratified_randomization_completed'\nORDER BY created_at DESC;\n```\n\n---\n\n## Acceptance Criteria\n\n✅ **All criteria must pass before production use:**\n\n- [ ] All non-deleted orgs assigned to Organizations\n\n**Symptom**: `SELECT COUNT(*) FROM public.orgs WHERE deleted_at IS NULL AND study_arm IS NULL;` returns > 0\n\n**Cause**: Migration or randomization script failed to complete\n\n**Solution**:\n```bash\n# Re-run randomization\npython backend/scripts/randomize_orgs.py --seed <same_seed>\n```\n\n### Issue: Imbalanced Arms\n\n**Symptom**: Arm sizes differ by > 1 within a tier\n\n**Cause**: Bug in allocation algorithm (unlikely with tested code)\n\n**Solution**: Check verification query 7 and inspect tier-specific logic\n\n### Issue: Duplicate Assignments\n\n**Symptom**: Verification query 4 returns rows\n\n**Cause**: Database corruption or concurrent updates\n\n**Solution**:\n```bash\n# Clear and re-randomize\npython backend/scripts/randomize_orgs.py --dry-run  # Preview\npython backend/scripts/randomize_orgs.py             # Execute\n```\n\n---\n\n## Design Decisions\n\n### Why Stratified Randomization?\n\nStratified randomization ensures:\n- **Balanced distribution by tier**: Enterprise, Mid-Market, and Startup orgs are equally represented in each arm\n- **Scientific validity**: Reduces confounding variables (org size, funding stage)\n- **Statistical power**: Enables tier-specific subgroup analysis\n\n### Why Deterministic Seeding?\n\n- **Reproducibility**: Same seed → same assignments (auditable, debuggable)\n- **Auditability**: Seed is stored, allowing reconstruction of allocation\n- **Testing**: Enables dry-runs and validation before production\n\n### Why Both SQL and Python?\n\n- **SQL function**: Simple one-time execution, minimal dependencies\n- **Python script**: CLI interface, detailed reporting, better error handling, dry-run capability\n\n---\n\n## Future
